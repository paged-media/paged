# ADR 217 — The showcase: one reference document built through the real editor

- **Status:** Accepted. Recorded retroactively on 2026-10-02 from the code at `28dc764`.
- **Scope:** `apps/canvas/tests/showcase/`, the Playwright project `showcase`, `.github/workflows/showcase-nightly.yml`, and the output directory `apps/canvas/showcase/`

## Context

The engine's generated fixtures each isolate one concern, and each plugin journey proves that
its own frame reaches the page. Nothing put engine features and all plugins into the same
document. `apps/canvas/tests/showcase/README.md:21-37` gives this as the reason for the
showcase and names two plugin defects that lived in that gap: both were "invisible to unit
tests" and were found only when a plugin frame was rendered and looked at.

The first version (commit `9989777`, 2026-08-21) built sixteen pages in one spec. Commit
`183a4b3` (2026-08-26) split the build into chapters, because a single spec at the size of
the full document would lose everything on a late failure
(`apps/canvas/tests/showcase/chapter.ts:22-23`). The document now has 134 pages
(`apps/canvas/tests/showcase/names-annual.ts:38`); `AUTHORING.md` calls it "The Paged Annual".

## Decision

One reference document is built by driving the running editor through its client, the same
path a user's input takes, and the build checks itself against three lists.

- The project `showcase` runs every spec in `tests/showcase` in one worker: the 38 chapter
  specs in file-name order, then `900-assemble.spec.ts`, then seven further specs, among
  them the driver's own tests and the two InDesign specs below. A chapter loads the previous chapter's `.paged` checkpoint through
  the ordinary open path, runs its page modules, saves the next checkpoint and writes a
  ledger fragment. The first chapter loads a base fixture generated by the engine's
  `paged-gen` from a `core` checkout beside the editor.
- For each module the runner snapshots the module's first page, runs the module and requires
  that the render changed. Modules marked `selfGated`, and modules marked `needsGpu` on a
  lane without WebGPU, are exempt and leave a note.
- The ledger counts three axes: feature-registry rows the modules claim, wire operations
  exercised (against the capability table) and property paths set (against the engine's
  introspection catalogue in the `core` checkout).
- The assembly exports the `.paged` container, the `.idml` twin, two PDFs and one PNG per
  page. It fails on a plugin part path with a doubled prefix, on an IDML export loss outside
  two allowed kinds, when the twin does not reopen with every page or a module-owned page
  is blank in it, and when a ledger count differs from `coverage-baseline.json` in either
  direction.
- Two further specs ask Adobe InDesign what it reads from the exported IDML and what it
  draws. They need macOS with InDesign installed and skip elsewhere. They call themselves
  "Not a CI lane"; no workflow sets `REQUIRE_REAL_INDESIGN`, which turns the skip into a failure.
- The outputs are committed in `apps/canvas/showcase/`, by hand; the nightly run uploads its
  outputs as workflow artifacts (`.github/workflows/showcase-nightly.yml:16-18`).

## Alternatives considered

Adding the document to the fidelity thresholds: forbidden in the showcase README (`:35-37`).
Comparing with InDesign's exported PDF: rejected because poppler renders InDesign's knockout
transparency groups wrongly, so the comparison uses InDesign's own raster (same file,
`:95-98`). One spec for the whole document: replaced by chapters (`chapter.ts:22-29`).

## Consequences

The lane needs the engine's source tree: the base fixture and the property-path catalogue
come from a `core` checkout beside the editor. The nightly workflow says it reintroduces a
checkout that `tests.yml` removed (`showcase-nightly.yml:4-9`); `tests.yml` also checks out
`core`, to build the fixture generator ([ADR 216](216-test-tiers.md)).

The registry axis depends on a repository that is not public. `chapter.ts:67` resolves it as
a sibling directory; when it is absent `loadRegistry` returns an empty map and
`buildCoverage` skips the existence and shipped checks. The nightly workflow checks out the
editor, `core` and plugin-doc, but not the registry. The closure over the whole registry is not armed
(`EXCLUSIONS_COMPLETE = false`, `apps/canvas/tests/showcase/exclusions.ts:64`).

The committed baseline is 196 registry rows, 117 operations and 201 property paths. A change
that raises a count must raise `coverage-baseline.json` in the same change.

The README has not followed the code. It still says "sixteen-page" and points at a `plan.ts`
that does not exist. It lists three assertions per spread, including that reported elements
exist; the chapter runner logs their count (`chapter.ts:337-344`) and has no such check.
`apps/canvas/playwright.config.ts:226-228` calls the project "Not part of any CI lane".
